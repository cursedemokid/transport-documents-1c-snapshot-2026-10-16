# TransportDocumentsOneS

FastAPI-сервис для интеграции транспортных документов между Saby/СБИС и 1С. Сервис получает входящие документы из Saby, ищет соответствующие документы в 1С, проверяет возможность записи входящих реквизитов и при необходимости формирует отчет.

Точка входа приложения: `main.py`.

**Состояние: запись в продуктивную 1С выключена.** Что проверено на живых данных
и что осталось до включения — в [READINESS.md](READINESS.md).

## Что делает сервис

- предоставляет HTTP API для проверки состояния сервиса и ручного запуска синхронизации;
- показывает сотруднику форму подтверждения: программа предлагает, человек решает;
- получает входящие транспортные документы из Saby/СБИС;
- ищет в 1С подходящие документы поступления дополнительных расходов;
- проверяет найденные документы перед записью;
- записывает входящий номер и дату из Saby в 1С — **только после подтверждения сотрудником**;
- поддерживает dry-run режим без фактической записи в 1С;
- формирует CSV/XLSX-отчеты и может отправлять их по SMTP;
- запускает ежедневную автоматическую синхронизацию внутри процесса FastAPI.

## Архитектура проекта

Основной поток выполнения:

1. FastAPI-приложение создается в `main.py`.
2. При старте приложения загружаются настройки через `Settings.from_env()`.
3. В `lifespan` создается `DailySyncScheduler`.
4. Планировщик запускает ежедневную синхронизацию, если она включена в настройках.
5. Ручной запуск синхронизации выполняется через `POST /sync/run`.
6. Основная бизнес-логика находится в `app/services/sync_service.py`.
7. `SyncService` использует клиентов Saby и 1С, выполняет поиск, валидацию, запись и формирование отчета.

HTTP API:

- `GET /` - статус сервиса.
- `GET /health` - healthcheck.
- `POST /sync/run` - ручной запуск синхронизации, под ключом `SYNC_API_KEY`.

Форма подтверждения — те же шесть маршрутов без логина, ворота у них код из
письма (см. «Подтверждение сотрудником»):

- `GET /confirm` - ввод кода.
- `POST /confirm/login` - вход по коду; код гаснет.
- `POST /confirm/resend` - выслать новый код на адрес из рассылки.
- `GET /confirm/list` - что ждёт решения.
- `POST /confirm/preview` - второе окно: что именно будет записано.
- `POST /confirm/apply` - запись в 1С.

Все шесть отвечают отказом при `CONFIRM_ENABLED=false`.

python -m venv .venv
```

.\.venv\Scripts\Activate.ps1
```

```powershell
pip install -r requirements.txt
```

```powershell
Copy-Item .env.example .env
```

После этого заполните в `.env` параметры подключения к Saby, 1С и SMTP.

## Настройка окружения

Настройки читаются в `app/config.py`. При вызове `Settings.from_env()` проект пытается загрузить первый найденный файл:

1. `.env`
2. `develop.env`

Если переменная уже задана в окружении ОС и не пустая, значение из файла не перезаписывает ее.

Рекомендуемый локальный сценарий:

```powershell
Copy-Item .env.example .env
notepad .env
```

Файл `.env` содержит секреты и локальные настройки. Его нельзя коммитить в репозиторий.

## Описание ключевых переменных окружения

### Saby/СБИС

Документы читаются реестром входящих через библиотеку `pysaby` по логину и паролю.

- `SABY_BASE_URL` - базовый URL Saby, например `https://online.sbis.ru`.
- `SABY_LOGIN` - логин Saby.
- `SABY_PASSWORD` - пароль Saby.
- `SABY_PAGE_SIZE` - размер страницы при чтении реестра, по умолчанию `200`.
- `SABY_MAX_PAGES` - предел страниц за прогон. Реестр СБИС игнорирует фильтр по датам и отсортирован по времени события, а не по дате документа, поэтому читается целиком; обрезка по пределу означает дыру в выборке и попадает в отчёт.
- `SABY_DOCUMENT_TYPES` - типы документов реестра, которые нас касаются; по умолчанию `ДокОтгрВх` (входящий УПД). Остальное в реестре — договоры, акты сверки, корректировки, счета — суммы в событии не имеет.
- `SABY_PAGE_RETRIES`, `SABY_RETRY_DELAY_SECONDS` - повторы чтения страницы реестра при обрыве связи.

### 1С

- `ONE_S_BASE_URL` - базовый URL API 1С.
- `ONE_S_USERNAME` - имя пользователя 1С.
- `ONE_S_PASSWORD` - пароль пользователя 1С.
- `ONE_S_WRITES_ENABLED` - отдельное разрешение HTTP-записей в 1С; по умолчанию `false`. При `false` клиент прекращает операцию до сетевого POST-запроса.
- `SYNC_API_KEY` - ключ для `POST /sync/run`, передаётся заголовком `X-API-Key`. При `ONE_S_WRITES_ENABLED=true` обязателен: без него запуск с записью был бы открыт всем, и сервис не стартует.

Дополнительно:

- `ONE_S_ALLOWED_WAREHOUSE_GROUPS` - группы складов из справочника, для которых разрешена автоматическая обработка. По умолчанию `ОСНОВНЫЕ`.
- `ONE_S_ALLOWED_EXPENSE_TYPES` - виды доп. расходов, обрабатываемые автоматически. По умолчанию `Фрахт,ЖД РФ`.
- `ONE_S_BULK_CHUNK_DAYS`, `ONE_S_BULK_MAX_CHUNKS`, `ONE_S_BULK_TIMEOUT_SECONDS` - параметры кусочного чтения заказов поставщику.
- `MATCH_MIN_SCORE`, `MATCH_SCORE_MARGIN`, `MATCH_NAME_SIMILARITY`, `MATCH_DATE_WINDOW_DAYS` - пороги сопоставления.
- `EXPENSE_LOOKBACK_DAYS`, `EXPENSE_LOOKAHEAD_DAYS` - насколько период выборки доп. расходов шире окна Saby.
- `ALLOW_COMPLETING_PARTIAL_REQUISITES` - дозаполнять документ, если в 1С проставлена только половина реквизитов.
- `ONE_S_AUTO_WRITE_ENABLED` - разрешить прогону записывать самостоятельно, без подтверждения человека; по умолчанию `false`. Пока выключено, ночной прогон только готовит предложения.
- `ONE_S_ORDER_DATE_SLACK_DAYS` - запас в днях при точечном поиске заказа и при перечитывании документа перед записью.
- `ONE_S_AUTO_PICKUP_ROW_NAME` - название строки табличной части «Даты», из которой берётся фактическая дата автовывоза.
- `ONE_S_AUTO_PICKUP_FIELDS` - имена плоских полей заказа с той же датой, если обмен начнёт их отдавать. По умолчанию пусто: основной источник — табличная часть.

### Контракт обмена с 1С

Методы чтения используют **HTTP GET с параметрами в JSON-теле**, для чего в `JsonHttpClient` есть отдельный метод `get_json()`.

| Метод | Назначение | Параметры |
|---|---|---|
| `GET /data1C/organization` | справочник организаций | нет |
| `GET /data1C/addexpensetype` | виды доп. расходов | нет |
| `GET /data1C/warehouse` | склады с группами | нет |
| `GET /data1C/docaddexpenses` | поступления доп. расходов | `periodBegin`, `periodEnd`, `deletemark`, `confirmed`, `organization`, `addexpensetype`, `ordertosupplier` |
| `GET /data1C/ordertosupplier` | заказы поставщику | `periodBegin`, `periodEnd`, `deletemark`, `confirmed`, `organization` |
| `GET /data1C/ordertosupplierattributes` | свойства одного заказа, включая табличную часть «Даты» | `docid` |
| `POST /data1C/updatedocaddexpenses` | запись входящих реквизитов | `docID`, `incomingdocnumber`, `incomingdocdate` |

Особенности, под которые написан слой обмена:

- Все значения приходят строками: суммы вида `1 191,06` с неразрывным пробелом U+00A0, булевы как `Да`/`Нет`, пустая дата как `01.01.0001 0:00:00`.
- Форм ответа три: `{"code": 200, "data": [...]}` при успехе, `{"code": 500, "data": "<текст исключения>"}` при ошибке обработчика и `{"code": 404, "error": "..."}` при ошибке маршрутизации.
- Передавать `ordertosupplier` пустой строкой нельзя - обмен отвечает HTTP 500. Пустые параметры не отправляются вовсе.
- Фильтра по номеру или идентификатору заказа поставщику нет: лишние параметры молча игнорируются, поэтому заказы читаются кусками и индексируются локально.
- ИНН и КПП обмен не отдаёт, поэтому контрагенты сверяются по наименованию с нормализацией.
- Табличная часть «Даты» приходит отдельным методом `ordertosupplierattributes` по идентификатору заказа и в уплощённом виде: имя свойства начинается с `ПЛАН `, `ФАКТ ` или `НОРМ `, дальше идёт название строки. Из неё берётся фактическая дата автовывоза, на которой держится основная проверка.
- Полей оптимистической блокировки при записи нет: документ перечитывается до записи и повторно после неё, и именно второе чтение решает, была ли запись успешной.

### Сервис, состояние и логи

- `APP_HOST`, `APP_PORT` - где слушает сервис. По умолчанию `127.0.0.1:8000`; для формы, видимой с рабочих мест, нужен `service.example.invalid`, и именно это задано в юните systemd.
- `SYNC_STATE_PATH` - файл памяти о последнем обработанном периоде, по умолчанию `state/sync_state.json`.
- `SABY_SESSION_PATH` - куда `pysaby` кладёт свою сессию, по умолчанию `state/saby_session.db`. Библиотека по умолчанию пишет её внутрь `site-packages`, где та теряется при переустановке и не пишется вовсе в окружении только для чтения.
- `REPORT_KEEP_FILES` - сколько файлов отчётов держать в `REPORT_DIR`; `0` — не чистить.
- `LOG_FILE` - файл лога с суточной ротацией. Пусто — только stderr (под systemd это journald).
- `LOG_LEVEL` - уровень корневого логгера, по умолчанию `INFO`.
- `LOG_BACKUP_DAYS` - сколько суток хранить старые файлы лога, по умолчанию `30`.

### Форма подтверждения

- `CONFIRM_ENABLED` - включает форму целиком. При `false` **все** её маршруты отвечают отказом, а прогон не готовит партию.
- `CONFIRM_BASE_URL` - адрес, по которому форма видна сотруднику; попадает ссылкой в письмо. Если пусто, письмо уйдёт с кодом и без ссылки, и сервис предупредит об этом при старте.
- `CONFIRM_PENDING_PATH` - партия, ожидающая решения, по умолчанию `state/pending.json`.
- `CONFIRM_JOURNAL_PATH` - журнал решений, по умолчанию `state/confirmations.jsonl`. Не ротируется и не чистится.
- `CONFIRM_CODE_TTL_HOURS` - сколько живёт код, по умолчанию `48`.
- `CONFIRM_SESSION_MINUTES` - сколько живёт открытая сессия, по умолчанию `30`; продлевается при каждом действии.
- `CONFIRM_MAX_ATTEMPTS`, `CONFIRM_LOCKOUT_MINUTES` - неудачных попыток ввода кода до паузы и длина паузы; по умолчанию `10` и `5` минут. **Счёт ведётся по выходному адресу**, а за NAT он один на весь офис, поэтому пороги мягкие: строгие закрывали бы форму всем из-за чужих опечаток. Настоящая защита здесь не пауза, а длина кода — 10 знаков из 32-буквенного алфавита.
- `CONFIRM_RESEND_INTERVAL_MINUTES` - как часто можно просить новый код, по умолчанию `5`. Пауза засекается при любом исходе, включая отказ по чужому адресу.

### Синхронизация

- `SYNC_WINDOW_DAYS` - период выборки по умолчанию в днях, если даты не переданы в ручном запросе.
- `SYNC_MAX_LOOKBACK_DAYS` - максимальная глубина поиска назад.
- `SYNC_MAX_ATTEMPTS` - количество попыток обработки технических ошибок.
- `SYNC_START_DATE` - нижняя граница поиска документов 1С.
- `AMOUNT_TOLERANCE` - допустимое расхождение суммы при сопоставлении.
- `DEFAULT_ORGANIZATION_NAME` - организация по умолчанию, если ее нет в документе Saby.
- `REQUEST_TIMEOUT_SECONDS` - timeout HTTP-запросов.

### Ежедневный запуск

- `DAILY_SYNC_ENABLED` - включает или отключает встроенный планировщик; по умолчанию `false`.
- `DAILY_SYNC_TIME` - время ежедневного запуска в формате `HH:MM`.
- `DAILY_SYNC_TIMEZONE` - часовой пояс запуска, по умолчанию `Europe/Moscow`.
- `DAILY_SYNC_DRY_RUN` - dry-run режим для автоматического запуска; по умолчанию `true`.
- `DAILY_SYNC_SEND_REPORT` - отправлять ли отчет после автоматического запуска.

### Отчеты и SMTP

- `REPORT_BACKEND` - backend отчетов: `smtp`, `console`, `both`, `none`.
- `REPORT_DIR` - директория для файлов отчетов, по умолчанию `reports`.
- `SMTP_REPORT_FORMAT` или `REPORT_FORMAT` - формат отчета: `xlsx` или `csv`.
- `SMTP_HOST` - SMTP-сервер.
- `SMTP_PORT` - SMTP-порт, по умолчанию `587`.
- `SMTP_USERNAME` - SMTP-пользователь.
- `SMTP_PASSWORD` - SMTP-пароль.
- `SMTP_FROM` - адрес отправителя.
- `ERROR_EMAIL_TO` или `SMTP_TO` - получатели отчёта, через запятую или точку с
  запятой. **Первым берётся непустой `ERROR_EMAIL_TO`**, и если он задан, то
  `SMTP_TO` не читается вовсе — порядок именно такой, хотя имя переменной этого
  не подсказывает.

  Этот же список решает, **кто вправе подтверждать запись в 1С**: форма
  принимает только адрес из него и только на него высылает код. То есть добавить
  человека в рассылку значит дать ему право санкционировать изменение
  бухгалтерских документов. Разных списков нет намеренно: кто получает отчёт,
  тот и подтверждает.
- `SMTP_CC` - получатели копии.
- `SMTP_BCC` - получатели скрытой копии.
- `SMTP_USE_TLS` - использовать STARTTLS.
- `SMTP_USE_SSL` - использовать SMTP over SSL.
- `SMTP_SUBJECT_PREFIX` - префикс темы письма.
- `SMTP_ATTACH_REPORT` - прикладывать файл отчета к письму.
- `SMTP_MAX_ATTACHMENT_MB` - максимальный размер вложения в мегабайтах. Если файл больше, письмо уходит без него, и причина пишется прямо в тексте письма.
- `SMTP_TIMEOUT_SECONDS` - предел ожидания SMTP, по умолчанию `30`. Без него зависший сервер держал бы поток планировщика, а такой поток не отменяется — процесс переставал гаситься вовсе.

Также поддерживаются алиасы в стиле Django: `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS`, `EMAIL_USE_SSL`, `DEFAULT_FROM_EMAIL`, `EMAIL_TO`, `EMAIL_BACKEND`.

## Запуск формы подтверждения одной командой

```bash
.venv/bin/python scripts/desktop.py
```

Поднимает сервис и открывает отдельное окно браузера сразу на форме
подтверждения. Обычный профиль браузера не трогается — окно работает во
временном каталоге. **Закрыли окно — сервис остановился**, порт освобождён,
временный каталог удалён. То же делает `kill` по SIGTERM.

При старте печатается, сколько документов ждёт решения и до какого времени
действует код из письма: если ждать нечего, это видно сразу, а не после ввода
кода.

На машине без графики браузер не открывается — печатается адрес, сервис держится
до Ctrl+C. Адрес и порт берутся из `APP_HOST` и `APP_PORT` (по умолчанию
`127.0.0.1:8000`); если порт занят, берётся любой свободный. Конкретный браузер
можно задать через `DESKTOP_BROWSER`.

## Ручной запуск синхронизации

Ручной запуск выполняется через `POST /sync/run`. Если задан `SYNC_API_KEY`,
запрос должен нести его в заголовке `X-API-Key`; при `ONE_S_WRITES_ENABLED=true`
ключ обязателен. Второй одновременный запуск получает `409`: прогон меняет общее
состояние, и двух сразу быть не может.

Пример dry-run запуска за конкретный период:

```powershell
Invoke-RestMethod `
  -Method Post `
  -Uri http://127.0.0.1:8000/sync/run `
  -ContentType "application/json" `
  -Body '{
    "date_from": "2026-08-17",
    "date_to": "2026-08-17",
    "dry_run": true,
    "send_report": true,
    "max_documents": 10
  }'
```

Тело запроса:

```json
{
  "date_from": "2026-08-17",
  "date_to": "2026-08-17",
  "dry_run": true,
  "send_report": true,
  "max_documents": 10
}
```

Поля запроса:

- `date_from` - начальная дата периода. Если не указана, используется окно по умолчанию.
- `date_to` - конечная дата периода. Если не указана вместе с `date_from`, используется текущая дата или одиночная дата.
- `dry_run` - если `true`, сервис выполняет проверки, но не записывает данные в 1С. Значение по умолчанию: `true`.
- `send_report` - если `true`, после запуска формируется и отправляется отчет. Значение по умолчанию: `true`.
- `max_documents` - ограничение количества документов Saby для обработки.

Ответ содержит `request_id`, период запуска, количество документов Saby, список результатов, признак отправки отчета и агрегированные счетчики `counts`.

## Автоматическая ежедневная синхронизация и scheduler.py

Автоматический запуск реализован в `app/services/scheduler.py` классом `DailySyncScheduler`.

`DailySyncScheduler` принимает объект `Settings`. В `main.py` он создается при старте FastAPI-приложения:

```python
settings = Settings.from_env()
scheduler = DailySyncScheduler(settings)
app.state.daily_sync_scheduler = scheduler
scheduler.start()
```

При остановке приложения вызывается:

```python
await scheduler.stop()
```

Поведение планировщика:

- если `DAILY_SYNC_ENABLED=false`, метод `start()` не создает задачу и планировщик не запускается;
- если `ONE_S_WRITES_ENABLED=false`, планировщик **запускается**, но прогон идёт холостым: он читает, сопоставляет и присылает отчёт, ничего не записывая. Это и есть режим наблюдения перед включением записи, и при старте об этом пишется предупреждение в лог;
- `DAILY_SYNC_TIME` задает время ежедневного запуска в формате `HH:MM`;
- `DAILY_SYNC_TIMEZONE` задает часовой пояс запуска, по умолчанию `Europe/Moscow`;
- планировщик работает как `asyncio` task с именем `daily-sync-scheduler`;
- до следующего запуска планировщик ожидает через `asyncio.wait_for()` и внутренний stop event;
- при остановке приложения `stop()` выставляет stop event, отменяет task через `cancel()` и дожидается завершения;
- каждый ежедневный запуск вызывает `SyncService.run()` в отдельном потоке через `asyncio.to_thread()`, чтобы синхронная бизнес-логика не блокировала event loop FastAPI;
- исключения внутри ежедневного запуска логируются, но не останавливают процесс приложения.

Настройки автозапуска:

```env
ONE_S_WRITES_ENABLED=false
DAILY_SYNC_ENABLED=false
DAILY_SYNC_TIME=17:00
DAILY_SYNC_TIMEZONE=Europe/Moscow
DAILY_SYNC_DRY_RUN=true
DAILY_SYNC_SEND_REPORT=true
```

Что означает каждая настройка:

- `DAILY_SYNC_ENABLED` - включает встроенный ежедневный запуск. Для отключения установите `false`.
- `DAILY_SYNC_TIME` - локальное время запуска в часовом поясе `DAILY_SYNC_TIMEZONE`.
- `DAILY_SYNC_TIMEZONE` - имя часового пояса из `zoneinfo`. Для `Europe/Moscow` есть fallback на UTC+3, если системная база часовых поясов недоступна.
- `DAILY_SYNC_DRY_RUN` - значение `dry_run`, которое будет передано в `SyncRunRequest` при автоматическом запуске.
- `DAILY_SYNC_SEND_REPORT` - значение `send_report`, которое будет передано в `SyncRunRequest` при автоматическом запуске.

Автоматический запуск не требует cron или Windows Task Scheduler, пока запущен процесс FastAPI. Если процесс остановлен, ежедневная синхронизация не выполняется.

## Отчеты и SMTP-настройки

Отчеты формируются в `ReportService` и сохраняются через `save_report_file()`.

Форматы:

- `xlsx`, если `SMTP_REPORT_FORMAT=xlsx` или `REPORT_FORMAT=xlsx`;
- `csv` для остальных значений.

Файлы отчетов сохраняются в директорию `REPORT_DIR`. Имя файла содержит период и `request_id`.

Backend отчетов задается переменной `REPORT_BACKEND`:

- `smtp` - отправить письмо через SMTP;
- `console` - вывести письмо и путь к отчету в stdout, без отправки;
- `both` - вывести в stdout и отправить через SMTP;
- `none` - сохранить отчет, но не отправлять письмо.

Минимальные SMTP-настройки для отправки:

```env
REPORT_BACKEND=smtp
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=developer@example.com
SMTP_PASSWORD=your_smtp_REDACTED
SMTP_FROM=developer@example.com
SMTP_TO=developer@example.com
SMTP_USE_TLS=true
SMTP_USE_SSL=false
```

Проверить настройки почты: `python scripts/send_test_email.py --print-config` показывает,
во что развернулись переменные (пароли скрыты) и уйдёт ли письмо. Без ключа скрипт
отправляет проверочное письмо тем же путём, которым уходят отчёты.

## Подтверждение сотрудником

Программа не принимает решений сама. Даже когда кандидат единственный и все
проверки пройдены, документ получает статус «Ожидает подтверждения», а запись
выполняет человек.

Как это устроено:

1. Прогон готовит предложения и складывает их в `state/pending.json`.
2. В письме с отчётом появляется код доступа — общий на рассылку.
3. Сотрудник открывает `/confirm`, вводит код, видит только то, что требует
   решения; остальное остаётся в приложенном Excel.
4. Отмечает нужные варианты, нажимает «Подтвердить», во втором окне видит
   поимённо, что будет записано, и соглашается.
5. Запись выполняется тем же путём, что и в прогоне: документ перечитывается,
   проверяется и записывается. Результат по каждой строке показывается сразу.

Входа по логину и паролю нет. Ворота — код из письма, и он **одноразовый**:
сработал один раз, открыл сессию и погас. Открытую сессию это не выбрасывает —
она живёт `CONFIRM_SESSION_MINUTES` и продлевается при каждом действии. Но
сессия привязана к своей партии: если прогон успел подготовить новую, форма
попросит код из последнего письма — ключи позиций в партиях одни и те же, и
работать со старой сессией по новому списку нельзя.

Перебор ограничен: `CONFIRM_MAX_ATTEMPTS` неудачных попыток — пауза на
`CONFIRM_LOCKOUT_MINUTES`. Считается это **по выходному адресу**, то есть за NAT
на весь офис сразу; поимённо различать людей без логина нечем, поэтому пороги
мягкие (см. описание переменных).

Что происходит после нажатия «Записать»:

| Исход | Что в 1С | Что с предложением |
|---|---|---|
| записано | номер и дата проставлены | уходит из списка |
| уже заполнено вручную | не тронуто | уходит из списка |
| в 1С другой входящий | не тронуто | уходит из списка, разбирать руками |
| запись запрещена настройкой | не тронуто | **остаётся**, попытку можно повторить |
| техническая ошибка | не тронуто | **остаётся**, попытку можно повторить |

Разница важная: раньше предложение исчезало при любом исходе, и решение человека
пропадало вместе с ним.

Потерял сессию или письмо — на экране ввода запрашивается новый код на свою
почту, письмо приходит сразу. Форма отвечает прямо: отправлено или нет и почему.
Чаще раза в `CONFIRM_RESEND_INTERVAL_MINUTES` минут запросить нельзя.

Прежний код при этом перестаёт работать — иначе и не могло быть: в хранилище
лежит только хэш, восстановить старый код нечем, поэтому высылается новый.
Побочно это к лучшему: утёкший код гаснет сам.

Кто подтвердил — видно из журнала `state/confirmations.jsonl`, и адрес туда
попадает двумя путями разной надёжности. Если человек запрашивал код на свою
почту, адрес уже известен: код одноразовый и уходит только на адрес из рассылки,
значит вошедший с ним читает тот ящик. Спрашивать нечего — форма показывает
адрес, а сервер берёт его из своей памяти и присланное значение не читает вовсе
(в куке лежит лишь непрозрачный ключ). Если код взят из общей рассылки, кто
именно вошёл, неизвестно, и адрес приходится назвать в поле — он так же
проверяется по списку. В журнале эти два случая помечены по-разному:
«код уходил на него» и «назван в форме», чтобы не выдавать слова за
свидетельство. Журнал дописывается,
не ротируется и не чистится: это ответ на вопрос, кто разрешил запись в
бухгалтерию. Код в нём хранится только хэшем.

Автоматическая запись без человека закладывается настройкой
`ONE_S_AUTO_WRITE_ENABLED`, но **выключена**. Включать её имеет смысл тогда,
когда на накопленных подтверждениях станет видно, что доля ошибок остаётся
нулевой.

## Dry-run режим

Dry-run режим позволяет проверить сопоставление и валидацию без записи входящих реквизитов в 1С.

Запись в 1С закрыта тремя независимыми предохранителями:

1. `SyncService` считает прогон тестовым, если запрошен `dry_run` **или** выключен `ONE_S_WRITES_ENABLED`. До попытки записи дело не доходит вовсе, поэтому запрет не превращается в техническую ошибку и не вызывает бессмысленных повторов.
2. `OneSClient.update_incoming_requisites()` проверяет флаг первой же инструкцией, до формирования тела запроса и до любого обращения к сети.
3. Человек: даже когда кандидат единственный и все проверки пройдены, прогон сам не пишет. Документ получает статус «ожидает подтверждения», а запись выполняется через форму — см. «Подтверждение сотрудником». Автоматическая запись закладывается отдельной настройкой `ONE_S_AUTO_WRITE_ENABLED` и выключена.

Планировщик в этот список не входит: при запрещённой записи он не отключается, а идёт холостым. Раньше здесь было написано обратное — это была ошибка документации, предохранителем он никогда не был.

Поэтому `dry_run=false` в ручном API-запросе не обходит запрет. В ответе и в отчёте видно фактический режим: поле `dry_run` показывает, была ли запись пропущена, а `writes_enabled` - разрешена ли она настройкой.

Для ручного запуска:

```json
{
  "date_from": "2026-08-17",
  "date_to": "2026-08-17",
  "dry_run": true,
  "send_report": true
}
```

Для автоматического ежедневного запуска:

```env
DAILY_SYNC_DRY_RUN=true
```

Если документ успешно найден и прошел проверки, но запись пропущена, результат получает статус `dry_run_ready`, а в сообщении указано, что именно её остановило: запрос или настройка.

При включённой записи цикл выглядит так: документ перечитывается непосредственно перед POST и проверяется заново, затем выполняется запись, затем документ перечитывается ещё раз. Успехом считается только подтверждённое чтением состояние - тело ответа 1С на это не влияет, поскольку его формат не задокументирован.

## Тестирование

Тесты написаны на `unittest`, дополнительных зависимостей для запуска не нужно:

```bash
python -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m unittest discover -s tests -t .
```

Ни один тест не выходит в сеть: базовый класс `tests/support/no_network.py` перехватывает `urlopen`, `smtplib` и `socket.connect`, поэтому случайный сетевой вызов падает с ошибкой, а не уходит в продуктивную 1С.

Из-за этого модульные тесты не заметят ни отвалившийся метод обмена, ни изменившийся формат ответа, ни закрывшийся доступ. Для этого есть отдельная сквозная проверка на живых данных:

```bash
.venv/bin/python scripts/system_check.py
```

Она проходит настройки, каждый метод обмена 1С по отдельности, выборку Saby, сквозной прогон, повторяемость, отчёты, предохранители записи, поведение при недоступной 1С и почту — и возвращает 0, если провалов нет. **Формы подтверждения она не касается**: та покрыта только модульными тестами, и проверять её приходится руками. Запись в 1С при этом не выполняется: при `ONE_S_WRITES_ENABLED=true` скрипт отказывается работать. Запускать перед каждым шагом раскатки и после любой правки. Отдельные тесты проверяют, что POST не выполняется ни при `dry_run=false`, ни при любых настройках, пока `ONE_S_WRITES_ENABLED=false`.

Фикстуры в `tests/fixtures/one_s/` повторяют форму реальных ответов обмена вместе со всеми неудобными местами: неразрывным пробелом в суммах, датой-заглушкой `01.01.0001`, строкой представления заказа и «грязными» наименованиями контрагентов. Настройки в тестах строятся через `tests/support/settings.py` и не читают локальный `.env`/`develop.env`.

Замер покрытия:

```bash
.venv/bin/python -m coverage run --source=app -m unittest discover -s tests -t .
.venv/bin/python -m coverage report
```

`tests/test_pysaby_contract.py` — канарейка на приватные методы `pysaby`: библиотека не отдаёт нужный метод реестра, поэтому запрос собирается вручную. Её обновление должно ломаться на тестах, а не на ночном прогоне.

## Возможные статусы результата синхронизации

- `written` - входящие реквизиты записаны в 1С и подтверждены повторным чтением документа.
- `dry_run_ready` - документ найден и проверки пройдены, но запись пропущена: либо запрошен dry-run, либо выключен `ONE_S_WRITES_ENABLED`.
- `already_filled` - в 1С уже стоят те же номер и дата.
- `not_found` - подходящее поступление доп. расходов не найдено. В сообщении указано, сколько документов просмотрено и сколько прошло по сумме и виду расхода.
- `ambiguous` - несколько кандидатов с равным весом, автоматический выбор невозможен. В сообщении перечислены кандидаты с их сигналами.
- `conflict` - в 1С заполнены другие номер или дата входящего документа. Такой документ не изменяется.
- `manual` - требуется ручная обработка: неподдерживаемый вид расхода, склад вне разрешённых групп, склад не найден в справочнике, заказ поставщику не указан или не выбирается однозначно, либо 1С не передаёт фактическую дату автовывоза.
- `business_error` - нарушено бизнес-правило: заказ поставщику отсутствует в выборке или дата УПД позже фактического автовывоза.
- `technical_error` - сбой при получении данных, поиске или записи. Повторяются только сбои сети и обмена; отказы по данным и настройкам не повторяются.

На каждый документ Saby в отчёт попадает ровно одна строка. Если документ обрабатывался повторно, в колонке «Попытка» стоит номер последней попытки.

## Развёртывание

### Требования

Python **3.11 или новее** (зафиксировано в `pyproject.toml`, проверено на 3.14).
Зависимостей четыре, все с точными версиями в `requirements.txt`. Ничего, кроме
интерпретатора и доступа в сеть, не нужно: ни базы данных, ни брокера, ни
внешнего планировщика.

### Сервис работает в ОДИН процесс

Это требование, а не предпочтение. В памяти процесса живут две вещи: блокировка
одновременных прогонов (`app/api/routes.py`) и сессии формы подтверждения
(`app/api/confirm.py`). Со вторым рабочим процессом два прогона пойдут разом —
оба будут писать состояние периода и оба смогут писать в 1С, а сотрудник,
вошедший по коду, на следующем запросе получит запрос кода заново.

```bash
python -m uvicorn main:app --host "$APP_HOST" --port "$APP_PORT" --workers 1
```

`--workers 1` обязателен. Если когда-нибудь понадобится несколько процессов,
сначала придётся вынести блокировку и сессии наружу — сейчас такого нет.

### Установка одной командой

```bash
sudo ./deploy/install.sh
```

Скрипт проверяет версию Python, заводит системную учётку без права входа,
копирует код в `/opt/transport-documents`, создаёт окружение, ставит
зависимости, раскладывает права и устанавливает юнит. Дальше он печатает три
оставшихся шага: заполнить `.env`, прогнать `system_check.py`, запустить службу.

**Повторный запуск обновляет установленное.** Код и зависимости заменяются;
настройки, состояние прогона, партия подтверждений, журнал решений, отчёты и
логи остаются нетронутыми.

Куда и под каким именем ставить — переменными окружения:

```bash
sudo TARGET=/srv/tdocs SERVICE=tdocs ./deploy/install.sh
```

Юнит ограничивает права: дерево приложения доступно только для чтения, на запись
открыты лишь `state/`, `reports/` и `logs/`. Сам юнит —
[deploy/transport-documents.service](deploy/transport-documents.service), если
понадобится ставить руками.

```bash
systemctl status transport-documents      # состояние
journalctl -u transport-documents -f      # логи
```

На Windows или там, где systemd нет, подойдёт любой менеджер процессов —
требование одно: один процесс и перезапуск при сбое.

### Куда пишет сервис

| Каталог | Что | Переносить при переезде |
|---|---|---|
| `state/sync_state.json` | последний обработанный период | да |
| `state/pending.json` | партия, ожидающая подтверждения | да |
| `state/confirmations.jsonl` | журнал решений: кто что разрешил | **обязательно** |
| `state/saby_session.db` | сессия pysaby | нет, создастся заново |
| `reports/` | файлы отчётов, хранится `REPORT_KEEP_FILES` штук | нет |
| `logs/` | логи с суточной ротацией | нет |

Все пути задаются переменными окружения и по умолчанию лежат рядом с
приложением — переносить установку можно копированием каталога.

### Логи

`LOG_FILE=logs/sync.log` включает файл с **суточной** ротацией: назавтра
вчерашний становится `sync.log.2026-09-15`, хранится `LOG_BACKUP_DAYS` суток.
Ротация по датам, а не по размеру, потому что вопрос к логу всегда звучит как
«что было четырнадцатого», а не «что было в предыдущем мегабайте».

В репозитории логов нет и быть не должно: `logs/` в `.gitignore`. Под systemd
всё, что уходит в stderr, дополнительно попадает в journald —
`journalctl -u transport-documents`.

### Планировщик — внутри сервиса

`DAILY_SYNC_ENABLED=true` включает ежедневный прогон в том же процессе; cron и
планировщик задач Windows не нужны. Так сделано намеренно: внешний планировщик
пришлось бы настраивать по-разному на каждой платформе, а требование —
разворачиваться одинаково везде. Прогон живёт в отдельном потоке, остановка
сервиса ограничена таймаутом и не ждёт конца прогона.

При запрещённой записи планировщик не отключается: прогон просто идёт холостым
и присылает отчёт — это и есть режим наблюдения.

### Секреты

`.env` и `develop.env` в `.gitignore` и в репозиторий не попадают — проверено,
ни одного файла с секретами в истории нет. Права на файл должны быть `600`.

Приложение читает `.env` само, из рабочего каталога. В юните `EnvironmentFile`
намеренно **не используется**: systemd разбирает такие файлы по своим правилам и
трактует `#`, `$`, `%` в значениях особо. В пароле 1С эти символы есть, и
подстановка исказила бы его молча — отказ выглядел бы как «1С не принимает
учётку», и причину искали бы не там.

## Рекомендации по эксплуатации

- Начинайте внедрение с `dry_run=true` и проверяйте отчеты до включения фактической записи.
- Оставляйте `ONE_S_WRITES_ENABLED=false`, пока запись в продуктивную 1С не будет отдельно разрешена. Планировщик при этом можно включать: прогон пойдёт холостым и будет присылать отчёт — это и есть режим наблюдения.
- Для ежедневного запуска явно задавайте `DAILY_SYNC_TIME`, `DAILY_SYNC_TIMEZONE`, `DAILY_SYNC_DRY_RUN` и `DAILY_SYNC_SEND_REPORT`.
- Настройте `REPORT_BACKEND=console` на тестовом окружении, чтобы проверять отчеты без отправки писем.
- Контролируйте директорию `REPORT_DIR`: файлы отчетов сохраняются на диск и могут накапливаться.
- Установите разумный `SYNC_MAX_ATTEMPTS`, чтобы повторять только технические ошибки и не создавать лишнюю нагрузку.
- Проверяйте `counts` в ответе `/sync/run` и статусы в отчете после каждого запуска.
- Запускайте **в один процесс** — см. раздел «Развёртывание».
- Задайте `LOG_FILE`, иначе ночной прогон нечем будет разбирать.

## Безопасность

- Не коммитьте `.env`, `develop.env`, пароли, access tokens и SMTP-секреты.
- Храните production-секреты в защищенном хранилище или переменных окружения среды запуска.
- Не отправляйте реальные токены и пароли в issue, pull request, чат или отчеты.
- Ограничьте доступ к `/sync/run`, если сервис доступен не только из доверенной внутренней сети.
- Используйте отдельные учетные записи для Saby, 1С и SMTP с минимально необходимыми правами.
