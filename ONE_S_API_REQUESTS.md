## 2. Ошибки в существующих методах

### 2.1. Падение на пустом параметре-ссылке

`GET /data1C/docaddexpenses` с `ordertosupplier: ""` отвечает HTTP 500:

```
{ОбщийМодуль.ОбменЕРП.Модуль(8301)}: Ошибка при вызове конструктора
(УникальныйИдентификатор): Недопустимое значение параметра (параметр номер '1')
```

Пустое значение должно означать «без фильтра» — так уже работает `organization`.
Обход на нашей стороне есть (параметр просто не отправляется), но это мина для
любого другого клиента.

### 2.2. Тип поля `data` меняется

Наблюдаются три разные формы ответа:

| Ситуация | Ответ |
|---|---|
| Успех | `{"code": 200, "data": [ ... ]}` |
| Исключение в обработчике | `{"code": 500, "data": "<текст исключения>"}` |
| Ошибка маршрутизации | `{"code": 404, "error": "Некорректный путь."}` |

`data` меняет тип со списка на строку, а текст ошибки лежит то в `data`, то в
`error`. Просьба привести к одной форме, например:

```json
{ "code": 500, "data": null, "error": { "message": "текст", "code": "ID_ERROR" } }
```

### 2.3. Неизвестные параметры игнорируются молча

`GET /data1C/ordertosupplier` принимает любые лишние параметры и возвращает
полную выборку. Проверено четыре варианта имени фильтра по заказу — все
проигнорированы, вернулось 2147 записей вместо одной. Опечатка в имени параметра
незаметно превращается в выкачивание всей базы. Просьба отвечать HTTP 400.

### 2.4. Значения приходят в виде для человека, а не для машины

- суммы — строкой с неразрывным пробелом и запятой: `"1 191,06"`, `"193 408,42"`;
- булевы — `"Да"` / `"Нет"`;
- пустая дата — `"01.01.0001 0:00:00"`.

Просьба отдавать числа числами, булевы как `true`/`false`, пустую дату как `null`.
Мы это уже разбираем, но любой формат «для глаз» рано или поздно меняется и
ломает разбор молча.

## 3. Фильтр по заказу поставщику

У `ordertosupplier` нет фильтра ни по номеру, ни по идентификатору. Чтобы найти
один заказ, приходится читать период кусками по три месяца и строить индекс в
памяти. За год это 2147 записей.

**Просьба:** добавить фильтрацию по `ИдентификаторДокумента` и по `Номер`.

Это же снимет и вторую проблему: в `docaddexpenses` поле `ЗаказПоставщику`
приходит **строкой представления**, а не ссылкой:

```
"ЗаказПоставщику": "Заказ поставщику ТД000001075 от 16.04.2026 0:00:00"
```

Мы разбираем её регулярным выражением. При любой перенастройке представления в
1С разбор сломается, причём молча. Просьба добавить рядом идентификатор:

```json
"ЗаказПоставщикуИдентификатор": "7e9061fe-d89a-55c4-a8c8-495cf7b0050b"
```

## 4. Недостающие поля

Сверено с колонками форм списка. В скобках — влияние на нашу логику.

**`docaddexpenses`** — нет 3 из 16 полей формы:

| Поле | Зачем |
|---|---|
| `Склад` | **Важно.** Склад берётся только из заказа поставщику. Замер на 2026 годе: из 91 поступления наших видов у 7 (8%) заказа нет вовсе, и группу склада определить нечем — такие документы уходят в ручную обработку независимо от остальных проверок. Уточните, заполняется ли поле в самом документе — на форме колонка выглядит пустой. |
| `Контрагент поставщика` | Указан в ТЗ как критерий сопоставления |
| `Вид операции` | Не используется, для полноты |

**`ordertosupplier`** — нет 3 из 19 полей формы:

| Поле | Зачем |
|---|---|
| `Закрыт заказ` | **Важно.** Закрытые заказы, вероятно, не должны обрабатываться автоматически |
| `Статус груза` | Может понадобиться для правил |
| `Дней до пост.` | Не используется, для полноты |

**Обе выгрузки:** нет `ИНН` и `КПП` ни у контрагента, ни у организации. Из-за
этого сопоставление контрагентов идёт нечётким сравнением наименований —
в 1С они «грязные», например `ВЕКТОР ООО (сверен на 31.12.2025)`. ИНН сделал бы
сопоставление надёжным.

**Справочник организаций** непригоден как ключ: 7 кодов повторяются (`УПР000005`
встречается трижды), наименования тоже (`прочее` ×9, `япрочее` ×11, `<>` ×7).
Нужен уникальный идентификатор, а лучше — ИНН.

## 5. Вопросы по методу записи

`POST /data1C/updatedocaddexpenses` мы **ещё ни разу не вызывали** — база
продуктивная, и без ответов на эти вопросы вызывать не будем.

1. **Что делает обработчик, если документ по `docID` не найден?** Возвращает
   ошибку или может что-то создать?
2. **Перепроводится ли документ при записи?** По ТЗ сервис не должен проводить и
   перепроводить документы. Если обработчик делает это внутри — изменятся
   движения по регистрам, и ограничение будет нарушено.
3. **Какой формат успешного и ошибочного ответа?** Сейчас неизвестен. Мы
   устойчивы к любому, но угадывать не хочется.
4. **Можно ли добавить проверку текущих значений?** Нужна защита от перезаписи
   ручных правок:

```json
{ "docID": "...", "incomingdocnumber": "72213", "incomingdocdate": "20260809",
  "expectedincomingdocnumber": "", "expectedincomingdocdate": "" }
```

При расхождении — отказ с отдельным кодом ошибки. Сейчас мы эмулируем это
перечитыванием документа до и после записи, но окно гонки остаётся.

5. **Есть ли тестовая база с той же публикацией?** Это лучший способ проверить
   запись, не трогая продуктив.

## 6. Уточняющие вопросы по чтению

1. **Включительны ли границы периода?** Попадёт ли документ с датой
   `06.08.2026 23:59:59` в выборку при `periodEnd=20260806`? Сейчас мы на всякий
   случай расширяем окно на сутки.
2. **Есть ли ограничение на размер ответа и пагинация?** Годовая выборка заказов
   отдаётся целиком; при росте базы ответ либо распухнет, либо начнёт молча
   обрезаться — второе опаснее.
3. **Что означает `organization: ""`** — все организации или ничего?
4. **Формат `incomingdocdate` в POST** — тот же `YYYYMMDD`, что и у периодов?
